# ADR-035: 릴리스 파이프라인은 한 곳에서 판정하고, 공개 저장소는 무언가 깨졌음을 배우는 자리가 아니다

**Status**: Accepted — 2026-08-24
**Date**: 2026-08-21
**Scope**: 릴리스 체크리스트와 그 게이트, release-decision 증거, 툴체인 결정성, 공개 저장소를 재생성하는 export, 태그에서 자산까지의 경로
**Related**: ADR-005 (Tauri governance), `docs/guides/public-private-ci-split.md`, `docs/guides/hybrid-import-workflow.md`, `docs/release-checklist.md`, `docs/contracts/release-decision-manifest.md`
**Issue**: #11330

## 구현 기록

수락은 아키텍처 방향을 확정할 뿐, 끝나지 않은 마이그레이션을 릴리스 증거로 바꾸지 않는다.
2026-08-24 현재 소스를 다시 측정한 결과는 다음과 같다.

| 결정 | 상태 | 현재 강제 장치 또는 남은 경계 |
| --- | --- | --- |
| D1 검증 동등성 | 부분 | stable canary는 공개 clippy 호출 3개와 기계적으로 일치한다. 공개 required check 15개 전부의 부모 PR 대응 레인은 아직 없다. |
| D2 정체성·신선도 | 구현 | manifest가 commit SHA와 artifact checksum에 결속되고 승인 시계는 manifest build에서 시작한다. 1시간 판정 창을 유지하는 이유는 계약 문서에 기록한다. |
| D3 체크리스트 disposition | 구현 | #11467 / PR #11472가 **현재 69개** 안정 ID 전부에 machine, evidence, human disposition을 부여하며 post-publish updater 항목도 포함한다. |
| D4 결정적 툴체인 | 부분 | #11324가 MSRV와 예약 stable-canary 검증을 추가했다. 정확한 빌드 툴체인 핀은 #11299가 계속 소유한다. |
| D5 export 승격 | 구현 | `update-public-repo-clone.sh`가 기존 export 브랜치를 이어 쓰고 provenance를 실제 부모에 결속하며 공개 base·브랜치 divergence를 거부한다. 회귀 테스트는 자손 양성 대조와 divergence 이식 대조를 모두 포함한다. |
| D6 단일 릴리스 진입점 | 부분 | #11256이 서명 능력 probe와 서명 태그 경로를 추가했다. manifest 생성은 여전히 별도 운영자 입력이므로 최종 조합은 후속 마이그레이션이다. |
| D7 발행 후 updater lifecycle | 구현 | 69개 등록부는 발행 전 updater 감지를 pending으로 보존하고 독립 post-publish receipt가 관측을 exact tag·commit에 결속한다. |

부분으로 표시한 행은 해당 릴리스 속성이 완료됐다는 증거가 아니다. 결정을 무기한 Draft로
두지 않으면서 마이그레이션 경계를 보존한다.

## Context

2026-08-21 에 `v0.0.1-rc.9` 가 자산 42개와 macOS 공증까지 마치고 나갔다. 거기까지
하루의 대부분이 걸렸고, 그 하루의 거의 전부는 **릴리스가 아니었다.**

다섯 가지가 잘못됐다. 그중 제품 결함은 **둘뿐**이라 구분해서 볼 가치가 있다.

**1 — 서명 없는 태그가 밀려 릴리스가 아무것도 만들지 못했다.** `release.yml` 은 태그
서명이 GitHub-verified 이기를 요구하는데, 그 검사는 태그가 존재해야 돌 수 있고 그
시점에 태그는 이미 push 됐다. 사전 게이트는 몇 분 전 `0 errors — OK to proceed` 였다.
published assets 0. 자산을 내지 못했던 이전 릴리스와 같은 모양이다.

**2 — 통과한 스모크를 자기 정리 코드가 실패로 뒤집었다.** macOS 설치 스모크가
`macOS installer smoke completed` 를 찍은 뒤, EXIT trap 이 아직 마운트된 DMG 위로
`rm -rf` 를 걸었다. 모든 경로가 `Read-only file system` 을 반환했고 `rm` 이 non-zero 로
끝났으며, 그것이 trap 의 마지막 문장이라 스크립트의 종료 상태가 됐다. `create-release`
가 그 잡을 needs 하므로 **모든 검사를 통과한 빌드가 발행되지 못했다.**

**3 — upstream 툴체인 릴리스가 공개 PR 전부를 막았다.** Rust 1.98.0 이 stable 이 되며
새 lint `clippy::chunks_exact_to_as_chunks` 가 `-D warnings` 아래에서 발화했다.
저장소에서 바뀐 것은 없었고 같은 소스가 하루 전 1.97.1 에서 통과했다.
`Check (fmt + clippy)` 가 required status check 라, Rust 변경이 하나도 없는 export
스냅샷까지 포함해 열려 있던 모든 PR 이 병합 불가가 됐다.

**4 — 그 lint 를 치우는 데 export 왕복 네 번이 들었다.** clippy 는 첫 실패 타깃에서
멈추므로 export 할 때마다 정확히 한 곳씩만 드러났다. 시도 한 번의 비용은 컴파일이
아니라 *부모 PR → 병합 → export 재생성 → 공개 PR → 승인* 전체였다. 같은 clippy 호출을
마침내 로컬에서 돌려 남은 것을 한 번에 보고 나서야 끝났다.

**5 — 증거 창이 유료 잡과 경합했다.** release-decision manifest 는 벤치마크 리포트의
`generated_at` 로부터 3600초 뒤 만료된다. 그 리포트를 만드는 desktop smoke 는 약 36분이
걸린다. 그 뒤의 모든 것 — manifest 생성, 게이트, 서명, 태그 — 이 남은 시간에 들어가야
했다. 계약 문서는 그 창이 왜 한 시간인지 말하지 않는다. "configured freshness window"
라고만 적혀 있다.

### 다섯 가지의 공통점

넷은 제품 결함이 아니다. **판정이 어디서 이뤄지는가**의 결과다.

| 측정 | 값 |
| --- | --- |
| 릴리스 체크리스트의 수동 체크박스 | 7개 섹션 **68개** |
| 공개 `main` 의 required status check | **15개**, strict, 머지 큐 없음 |
| release-decision 신선도 창 | 3600초, **문서화된 근거 없음** |
| Rust target 을 설치하는 지점 | **10곳**, 그중 하나가 `release.yml` |
| 공개에만 존재하는 검증 | `Check (fmt + clippy)` 를 비롯한 required 전체 |

파이프라인에 게이트가 부족한 게 아니다. **되돌리기 어렵거나 비싼 단계 이후에만 답할 수
있는 자리가 너무 많다.** 태그는 서명이 판정되기 전에 존재해야 하고, export 는 required
체크가 말하기 전에 발행돼야 하며, 유료 스모크는 그것을 제약하는 시계가 시작되기 전에
끝나야 한다.

우발적이 아니라 구조적인 발견이 둘 더 있다.

- **아무도 실행하지 않는 가드가 있었다.** 2026-08-21 기준 macOS 설치 preserve 테스트는
  **호출자가 0** 이었다. 이후 export 가드 체인에 배선했으므로 오늘 확인하는 사람은 1을
  본다. 이 워크스페이스에서 `cargo clippy` 를 도는 유일한 워크플로는 dispatch 전용이라
  스스로 돈 적이 없다 — 그쪽은 아직 열려 있다.

  위 표의 모든 수치는 2026-08-21 에 잰 것이고, 일부는 이 ADR 이 촉발한 작업으로 이미
  바뀌고 있다. **현재 상태에 대한 주장이 아니라 결정의 근거로 기록한 관측이다.**
- **필수 속성이 측정되지 않은 채 `OK to proceed` 를 내는 게이트는 없는 게이트보다 나쁘다.**
  증거처럼 읽히기 때문이다.

목표 케이던스인 **주 1회 이상**에서 68개 수동 체크리스트는 유지 불가능하고, 네 번 왕복하는
수정 루프는 감당 불가능하다.

## Decision

**릴리스를 막을 수 있는 모든 속성은 그것을 고치기 비싸게 만드는 단계 이전에 판정되고,
공개 저장소는 이미 통과한 트리만 받는다.**

여섯 가지 약속이 따른다.

### D1. 검증 동등성 — 판정은 내부에서

공개 `main` 의 모든 required check 는 부모 PR 에서 **같은 입력·같은 호출**로 도는
대응물을 갖는다. export 는 이미 그것을 통과한 트리만 나른다.

동등성은 관행이 아니라 기계로 강제한다. 가드가 양쪽에서 호출 집합을 뽑아 정규화하고
다르면 실패한다. required check 와 **다른 feature 집합**을 린트하는 canary 는, 병합을
막는 게이트가 red 인데 green 을 보고한다.

**동등성은 호출뿐 아니라 툴체인까지 포함한다.** 서로 다른 컴파일러에서 같은 명령은 다른
검사다 — 실패 3이 정확히 그렇게 일어났다. 그래서 파리티 가드는 해석된 툴체인도 비교하며,
D4 의 핀은 양쪽에 함께 적용되거나 어느 쪽에도 적용되지 않아야 한다. 한쪽만 고정된 상태는
모든 가드가 green 을 보고하는 채로 **D1 을 조용히 거짓으로 만든다.**

실패 4의 왕복을 없애는 것이 이것이다.

### D2. 증거는 정체성에 먼저 묶이고, 창은 파이프라인에 맞게 잡는다

release-decision 증거는 **이 커밋과 이 산출물**을 — commit SHA 와 artifact checksum 으로
— 증명해야 한다. 정체성이 1차 결속이며, 현재 계약이 덜 쓰고 있는 쪽이다.

**정체성만으로는 부족하고, 이 ADR 의 이전 초안은 그렇다고 말한 점에서 틀렸다.** 스모크
증거는 **환경 의존적**이다. 같은 커밋이라도 러너 이미지가 바뀌면 결과가 달라지고,
의존성이 yank 되거나 새 권고가 나올 수 있다. 증거를 영원히 두면 세상이 바뀐 커밋의 몇 달
된 관측 위에서 릴리스가 나갈 수 있다. **그 감쇠가 신선도 창의 진짜 논거이며 정체성
결속으로 대체되지 않는다.**

대체되지 않는 것은 창의 존재이지 **파이프라인을 고려하지 않고 잡은 크기**가 아니다.
현재 3600초는 벤치마크 리포트의 `generated_at` 기준인데 그 리포트를 만드는 잡이 약 36분
걸린다 — manifest 생성·게이트·서명·태그가 남은 시간을 나눠 쓴다. 계약은 왜 한 시간인지
말하지 않고 "configured freshness window" 라고만 적는다.

따라서 창은 유지하되, **모델하는 감쇠를 명시하고**, 그것을 먹이는 관측이 아니라 **판정
시점**부터 잰다. 자기 파이프라인을 담지 못하는 창은 릴리스를 보호하는 게 아니라 운영자를
서두르게 한다.

"판정 시점" 을 *단일 진입점(D6)이 도는 때* 로 읽어서는 안 된다. 그렇게 읽으면 이 단계가
마이그레이션의 마지막 단계를 기다리게 된다. 판정 시점은 **manifest 생성**이며, 그것은
오늘 이미 존재하고 증거·커밋·산출물이 함께 묶이는 지점이다. D6 는 나중에 그 시점을 하나의
명령으로 감쌀 뿐 그것을 만들지 않는다.

### D3. 체크리스트는 남고, 확인이 수동으로 남지 않는다

68개 항목 전부 유지한다. 각 항목은 정확히 하나의 disposition 을 갖는다.

| disposition | 뜻 |
| --- | --- |
| `machine` | 명령이 단언하고 증거를 남긴다. 실패는 차단한다. |
| `evidence` | 명령이 산출물을 모으고 사람이 읽고 서명한다. |
| `human` | 기계화할 수 없는 판단. 등록부가 **이유**를 기록한다. |

항목 → disposition → 명령을 잇는 등록부를 둔다. disposition 이 없는 항목이 있으면 가드가
실패하므로, 새 항목이 산문으로 들어올 수 없다. `human` 은 정당한 답이지만 **검토되지 않은
항목은 아니다.**

**등록부가 키를 잡으려면 항목에 안정적인 식별자가 먼저 필요하다.** 지금 여러 항목이 여러
줄에 걸쳐 있어 텍스트로 뽑으면 조각이 나온다 — 하나는 `Any` 라는 단어 하나로 나온다.
산문은 키가 아니다. 누가 문장을 다듬으면 바뀌고, 그 위에 세운 등록부는 매핑을 조용히
잃는다. 항목에 ID 를 부여하는 것이 이 단계의 **첫 수순**이지 뒷일이 아니다.

분류는 **언제 대상을 관측할 수 있는지**도 표현해야 한다. D7에는 발행 전에는 runtime 증거가
존재할 수 없는 항목이 있다. 이를 `human`으로 표시하거나 mock test를 실제 관측으로 가장하면
운영자가 검증 불가능한 것을 체크하게 된다. 등록부는 하나의 보이는 체크리스트 안에서
pre-publish와 post-publish 단계를 구분한다.

여러 항목이 곧 required check 다 — "Quick suite (PR CI) — all green" 이 그렇다. 그것들의
소유자는 D1 이고, 등록부는 **명령을 다시 적는 대신 레인을 참조한다.** 같은 호출을 두 곳이
들고 있는 것이 canary 와 required check 가 어긋날 뻔한 방식이고, 이 ADR 이 파리티 가드를
세운 이유다. 명령을 복사하는 disposition 등록부는 그 실패를 한 층 위에서 다시 만든다.

### D4. 툴체인은 결정적이고, drift 는 우리 일정에 발견된다

빌드 툴체인을 고정한다. Rust target 을 떠 있는 채널에 설치하는 지점이 열 곳이므로,
고정은 그 열 곳을 함께 갱신하는 **자기 자신의 변경**이다 — 정확한 버전 핀은 cargo 를 그
target 이 하나도 없는 별개 툴체인 항목으로 보낸다.

고정만 하면 업그레이드 전까지 새 lint 가 숨는다. 그래서 예약된 canary 가 required check
와 **같은 호출**로 최신 stable 을 시험한다. 새 릴리스의 lint 가 export 도중 얼어붙은
저장소가 아니라, 우리가 고른 날의 보고서로 도착한다.

### D5. export 는 승격이며, 공개 저장소를 덮어쓰기를 거부한다

두 가지를 바꾼다.

- export 브랜치는 **fast-forward 가능**해야 한다. 지금은 재생성이 base 에서 시작하므로
  수정본이 자손이 아니라 형제가 되어 열린 PR 을 갱신하지 못한다. 수정 하나가 새 브랜치,
  새 PR, 새 승인을 요구한다.
- **마지막으로 기록한 스냅샷 이후 공개 브랜치가 움직였으면 export 는 실행을 거부한다.**
  공개 기여는 부모로 import 된 뒤 다음 재생성에 다시 나타난다
  (`docs/guides/hybrid-import-workflow.md`). 그 import 가 들어오기 전에 재생성하면 기여가
  **조용히 되돌려진다.** 지금 그 순서는 강제 장치 없는 문서상 규율이다.

  비교 기준은 "부모에 없는 커밋" 일 수 없다. 두 저장소는 히스토리를 공유하지 않으므로
  SHA 가 대응하지 않는다. export provenance 가 이미 필요한 것을 기록한다 — 부모 커밋인
  `ssot.source_sha` 와 스냅샷이 기반한 공개 커밋인 `public_target.base_sha`. 따라서
  divergence 는 *공개 HEAD 가 기록된 `base_sha` 를 우리 export 커밋이 아닌 것으로 지나쳤다*
  이며, 거부는 그것을 검사한다.

### D6. 판정에서 자산까지 진입점 하나

릴리스는 게이트를 돌리고, 증거를 만들고 검증하고, 서명 키가 서명할 수 있음을 증명하고,
서명 태그를 만들고, 보고하는 **단일 명령**이다. 운영자가 순서를 기억해야 하는 단계는 없다.

서명 검사가 이 경로 전체의 본보기다. 태그가 없으면 서명은 검증할 수 없지만 **서명을 만들
수 있는지는** 확인 가능하다 — 설정을 읽는 대신 버릴 바이트에 실제로 서명해서. `user.signingkey`
가 설정돼 있다는 것은 키가 존재하고 읽히고 잠겨 있지 않다는 뜻이 아니다.

### D7. 업데이터는 존재하지만 실제 감지 증거는 발행 뒤에만 생긴다

이 ADR의 첫 측정은 Tauri plugin 설정만 보고 updater가 배선되지 않았다고 결론 냈다. 그
결론은 불완전했다. Maekon은 `src-tauri/src/updater`의 custom updater를 제공한다. stable
채널은 GitHub `/releases/latest`, prerelease 채널은 `/releases?per_page=1`을 조회하고 서명된
플랫폼 자산을 선택한다. 두 채널은 mock API 테스트로 검증되고, ignore된 network 테스트는
실제 GitHub Releases API까지 도달한다.

따라서 빈 `plugins.updater` endpoint와 Tauri update manifest 부재는 updater 부재의 증거가
아니다. Maekon이 Tauri updater plugin을 전달 adapter로 사용하지 않는다는 사실만 증명한다.

남은 결함은 lifecycle 순서다. release-decision manifest는 태그 전 승인 gate지만, *"이전
RC가 새 버전을 감지한다"*는 관측은 서명 태그가 공개 GitHub Release를 만든 뒤에만 가능하다.
이를 태그 전에 pass하도록 요구하면 불가능한 순환이 생기고, mock 테스트를 pass 근거로 쓰면
구현 증거와 runtime 증거를 섞게 된다.

그래서 이 결정은 세 가지를 말한다.

- **파이프라인이 두 단계를 모두 소유한다.** 발행 전 승인은 updater 감지 항목을 명시적
  `pending`으로 남기고, 발행 후 완료는 exact tag·commit에 결박된 이전 RC runtime receipt를
  요구한다.
- **되돌리기는 필요해지기 전에 연습한다.** 가장 최근에 실제로 밟은 복구는 수동이었고
  문서화돼 있지 않았다: 릴리스 객체 부재 확인 → 태그 삭제 → 재생성. 그것이 통한 이유는
  실패가 **자산 발행 이전**에 났기 때문이다. `docs/guides/updater-rollback-windows.md` 는
  아무도 걸어보지 않은 길을 설명한다.
- **체크리스트 항목이 lifecycle을 앞질러서는 안 된다.** post-publish 항목은 발행 전 pending일
  수 있지만 사라지거나 mock-test pass로 바뀌거나 RC 운영 완료의 근거가 될 수 없다.

이 정정은 updater를 재설계하지 않는다. 실제 shipped adapter를 아키텍처 정본으로 만들고,
승인과 뒤따르는 전달 증거를 분리한다.

## Alternatives rejected

**공개 저장소를 없애거나 자동 미러링한다.** 공개 저장소는 외부 기여 표면이고, 분리는
secret·서명·비공개 검증을 유지보수자 쪽에 둔다. 자동 미러링은 그 경계를 새게 하거나 검토
지점을 잃는다.

**체크리스트를 줄인다.** 68개 전부 필요하다. 문제는 항목의 존재가 아니라 **사람이
실행한다는 것**이다.

**공개 required check 를 권고로 낮춘다.** 사용자 앞의 마지막 게이트다. 마찰을 줄이려고
실제 속성을 일정과 바꾸는 것이다.

**CI 로그를 계속 쫓는다.** 측정으로 기각한다. 첫 실패 타깃에서 멈추는 도구는 실행당 한
건만 보고하므로 루프 길이가 지점 수와 같다. 같은 호출을 로컬에서 돌리자 전체가 한 번에
나왔다.

**머지 큐를 켠다.** 옳은 발상이지만 이 결정 기록의 자리가 아니다. 두 저장소 모두 strict
필수 체크를 쓰면서 **머지 큐가 없다.** 그래서 하나가 병합될 때마다 base 가 움직여 다음
브랜치가 낡고, auto-merge 는 그것을 스스로 풀지 못한다. 수정을 연달아 넣으려면 건마다
동기화·재실행 사이클이 붙는데, 그것이 오늘 하루가 길어진 큰 몫이었고 **D1 의 파리티
레인이 배가할 바로 그 비용이다.**

큐는 그 모양에 대한 표준 해법이지만, 켜는 순간 이 ADR 이 다스리는 클라이언트 릴리스
경로가 아니라 **모노레포의 모든 워크스페이스**의 병합 방식이 바뀐다. 이 레지스트리가
다루지 않는 이해관계자가 있다. 여기 슬쩍 넣지 않고 별도로 낸다.

## Migration

각 단계가 단독으로 병합할 가치를 갖도록 정렬했다.

1. **required 집합의 검증 동등성** (D1). 왕복을 없앤다. 가치가 가장 크고, 이후 모든
   단계의 검증을 싸게 만든다.
2. **체크리스트 disposition 등록부와 가드** (D3). 68개 산문을 기계가 읽는 계약으로
   바꾼다. 아무것도 지우지 않는다.
3. **증거 정체성 결속** (D2). 시계 경합을 없앤다.
4. **target 설치 10곳을 함께 갱신하는 툴체인 고정 + canary** (D4).
5. **export 승격과 divergence 거부** (D5).
6. **연습된 되돌리기와 명시된 롤아웃 단계** (D7). 단일 진입점보다 **의도적으로 먼저** 둔다
   — 되돌아갈 길을 시험하지 않은 채 더 빨리 내보내는 명령은 최악의 결과를 더 싸게 만든다.
7. **단일 릴리스 진입점** (D6). 위 여섯을 조합하므로 마지막이다.

## Consequences

- **내부 CI 비용이 오른다.** 동등성 레인은 공개 저장소가 이미 하는 일을 중복한다. 교환은
  한정적이고 의도적이며, 그것이 없애는 왕복이 더 비쌌다.
- **disposition 등록부는 유지해야 할 산출물이 된다.** 화석화하도록 두면, 아무것도 재지
  않으면서 증거처럼 읽히는 다음 물건이 된다.
- **divergence 거부는 의도적으로 마찰을 만든다.** import 되지 않은 공개 커밋은 유지보수자가
  가져올 때까지 재생성을 막는다. 의도한 동작이고, 외부 기여가 처음 들어오는 순간 체감된다.
- **툴체인 고정은 새 lint 를 업그레이드 시점으로 몬다.** canary 가 그것을 기습으로 만들지
  않게 하고, 그 canary 는 required check 와 같은 호출을 돌 때만 작동한다.
- **릴리스가 claim 이 필요한 작업이 된다.** 여러 에이전트가 기본 브랜치에 동시에 병합하고
  ruleset 은 strict 인데 머지 큐가 없다 — 자기 체크가 도는 동안 브랜치가 낡는다. 그래서
  D6 의 단일 명령에는 claim 이 필요하다. 없으면 두 릴리스가 엇갈리며 **각자 자기가 검증한
  head 를 쥐고 있다고 믿는다.**
- **파리티 중복 비용은 PR 당 약 17분이다.** 2026-08-21 에 공개 `Check (fmt + clippy)`
  잡에서 실측했다. D1 이 미러링할 세 조합을 그대로 도는 잡이다 — **green 17분 05초**,
  **red 5분 16초**. red 가 싼 이유는 clippy 가 첫 실패 타깃에서 멈추기 때문이다.

  따라서 교환은 *모든 클라이언트 PR 에 17분* 대 *문제가 있을 때의 export 왕복* 이다.
  왕복은 부모 병합 → 재생성 → 공개 PR → 공개 CI 이고, 거기서 clippy 잡만 같은 17분,
  `Test` 잡은 실측 55분이었다. 레인이 충분히 자주 발화할 때만 좋은 거래다. 오늘의 연쇄는
  그럴 것임을 시사한다 — 정리한 세 lint 중 둘(`useless_format`, `ok_expect`)은 이미 트리에
  있었고 컴파일이 첫 크레이트를 지나서야 드러났다. **파리티 레인이었다면 export 없이
  보고했을 것들이다.**

  이 추정은 공개 CI 의 hosted 수치다. 내부 레인은 하드웨어가 다르므로 1단계가 그것을
  물려받지 말고 **거기서 다시 재야 한다.**
- **자격증명 만료가 일정 관리 대상이 된다.** 주 1회 릴리스는 인증서·공증 수명을 분기 1회보다
  훨씬 자주 만나는데, 오늘 다가오는 만료를 태그 전에 알려주는 것이 없다.

## Non-goals

- **hybrid import 자동화.** `docs/guides/hybrid-import-workflow.md` 가 저위험 공개 PR 5건
  처리를 선행 조건으로 두며, 이 ADR 은 그것을 단축하지 않는다.
- **공개 export 승인 주체 변경.** 유지보수자 승인은 그대로다.
- **서버 아키텍처나 그 릴리스 경로에 대한 변경.**
- **required status check 집합의 구성 검토.** 이 ADR 은 15개를 주어진 것으로 두고,
  그것을 내부에서 먼저 판정하라고만 요구한다(D1).

  이 제외는 암묵으로 두지 말고 명명할 가치가 있다. **D3 가 공격하는 문제와 같은 모양**
  이기 때문이다. dispatch 전용 레인은 자기 존재를 정당화해야 한다 —
  `scripts/ci/release_gate_registry.json` 이 각각의 `why` 를 기록하고, 어느 map 에도 없는
  새 레인이 나타나면 가드가 실패한다. **모든 병합을 막는** 체크에는 같은 요구가 없다.
  어떤 문서도 체크를 required 로 만드는 기준을 말하지 않으므로, 그 집합은 68개 체크리스트와
  똑같이 누적으로 자란다.

  여기서 제외하는 이유는 그 집합이 클라이언트 릴리스 경로가 아니라 **저장소 전체**를
  막기 때문이다. 바꾸려면 이 레지스트리가 다루지 않는 이해관계자가 있다 — 머지 큐를
  밖에 둔 것과 같은 경계다. 자기 결정에서 D3 대우를 받아야 한다.

## Amendments

### 2026-08-25 — 명시적인 게시 경계

초기 D3/D7 레지스트리는 updater detection만 `post_publish`로 재정의했다.
릴리스 리허설에서 두 순환이 추가로 드러났다. 태그 전 manifest가 자기 자신의 검증
영수증을 요구했고, signed tag·GitHub Release·최종 asset이 생기기 전에 그 증거를
요구했다. 이제 레지스트리는 `pre_publish`, `publish_boundary`, `post_publish`을
구분한다. 승인 전 필수 통과는 첫 단계뿐이며, 나머지 두 단계는 해당 비가역 경계가
정확한 tag·commit 결속 영수증을 만들 때까지 명시적인 pending으로 남는다. 이는
라이프사이클 정합성 수정이지 검증 완화가 아니다. 게시 후 claim을 게시 전 증거로
바꾸지 않는다.
